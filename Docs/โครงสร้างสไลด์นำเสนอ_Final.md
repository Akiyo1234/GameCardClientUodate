### สไลด์ที่ 3: ภาพรวมระบบและการเล่นหลัก (Core Gameplay Loop)
* **หัวข้อสไลด์:** กลไกการเล่นหลักของเกม (Core Loop)
* **เนื้อหาบนสไลด์:**
  * **กติกาอ้างอิง:** ประยุกต์ใช้กลไกการสร้างขุมพลังทรัพยากร (Engine-Building) จากบอร์ดเกม **Splendor**
  * **5 ทรัพยากรระบบคอมพิวเตอร์:** CPU, RAM, Network, Storage, Security
  * **3 แอคชั่นในแต่ละเทิร์น (เลือกทำ 1 อย่าง):**
    1. หยิบเหรียญทรัพยากรจากกองกลาง
    2. ซื้อการ์ดโมดูลซอฟต์แวร์ (เพื่อรับแต้มดาว + โบนัสส่วนลดถาวร)
    3. จองการ์ดเก็บไว้บนมือ (เพื่อสกัดคู่แข่ง + รับเหรียญทอง Wildcard)
  * **เงื่อนไขชัยชนะ:** สะสมแต้มดาวครบ **20 แต้ม** เป็นคนแรก
* **รูปภาพประกอบ:**
  * `[รูป: หน้าจอการเล่นหลักในสนามรบ (Gameplay Screen) ชี้ตำแหน่งกองกลาง หน้าตักผู้เล่น และการ์ด 3 Tiers บนกระดาน]`
* **บทพูดนำเสนอ (Presenter Note):**
  * *"กติกาหลักคือผู้เล่นจะแข่งกันบริหารเหรียญทรัพยากรคอมพิวเตอร์ทั้ง 5 ประเภท นำไปซื้อการ์ดโมดูลซอฟต์แวร์ 3 ระดับ ซึ่งการ์ดแต่ละใบจะให้แต้มคะแนนและโบนัสทรัพยากรลดราคาถาวรเพื่อซื้อการ์ดถัดไปได้ง่ายขึ้น ใครสะสมครบ 20 แต้มก่อนจะเป็นผู้ชนะครับ"*

### สไลด์ที่ 4: ควิซแทรกชิงเทิร์นการเล่น (Interventional Quiz Mechanic)
* **หัวข้อสไลด์:** กลไกการสอดแทรกความรู้ (Gamified Quiz)
* **เนื้อหาบนสไลด์:**
  * **กติกาชิงเทิร์นเดินหมาก:** ทุกๆ 3 รอบการเล่น เกมจะหยุดและเด้งหน้าคำถามควิซให้ตอบพร้อมกันทุกคน
  * **ความรู้คอมพิวเตอร์ 5 หมวด:** สุ่มโจทย์สอดคล้องกับสีทรัพยากรในการ์ด
  * **เงื่อนไขชิงสิทธิ์:**
    * ตอบถูกและเร็วที่สุด (อันดับ 1) → ได้รับเหรียญทองพิเศษ + ได้เดินเทิร์นก่อนเป็นคนแรกในรอบถัดไป
    * ตอบถูกลำดับถัดมา (อันดับ 2-4) → ได้ลำดับเทิร์นเดินถัดไป
    * ตอบผิด → ตกไปอยู่ลำดับเทิร์นสุดท้าย
* **รูปภาพประกอบ:**
  * `[รูป: หน้าจอป๊อปอัพคำถามควิซ (Quiz Panel Interface) มีเวลานับถอยหลัง 10 วินาที และหน้าจอสรุปผลลำดับเทิร์นใหม่]`
* **บทพูดนำเสนอ (Presenter Note):**
  * *"จุดต่างสำคัญที่ทำให้เกมนี้เป็นสื่อการศึกษาคือระบบควิซแทรกทุก 3 รอบครับ ผู้เล่นต้องตอบคำถามแข่งกับเวลา 10 วินาที คนที่ตอบถูกและเร็วที่สุดจะได้สิทธิ์เดินก่อนในรอบถัดไปและได้เหรียญทอง เป็นการแปลงความรู้มาเป็นความได้เปรียบในตัวเกมครับ"*

### สไลด์ที่ 5: สถาปัตยกรรมระบบแบบ 3-Tier (System Architecture)
* **หัวข้อสไลด์:** สถาปัตยกรรมและเทคโนโลยีที่ใช้ (Tech Stack)
* **เนื้อหาบนสไลด์:**
  * **Client (ตัวเกม):** พัฒนาด้วย Unity 6 และภาษา C# รันกติกา แสดงผล UI แอนิเมชัน และระบบบอท AI
  * **Realtime Network (ระบบเชื่อมต่อ):** ใช้ Photon Fusion 2 (Shared Mode) ผ่านโปรโตคอล UDP ซิงโครไนซ์ควิซและลำดับเทิร์นเรียลไทม์
  * **Cloud Backend (คลาวด์หลังบ้าน):** ใช้ Supabase (PostgreSQL) ดูแล Auth, จับคู่ Matchmaking และข้อมูลสถิติประวัติ
* **รูปภาพประกอบ:**

### สไลด์ที่ 6: การออกแบบโครงสร้างฐานข้อมูลและคลังข้อมูล (Database Schema & JSON)
* **หัวข้อสไลด์:** โครงสร้างข้อมูลระบบหลักและคลังข้อสอบแบบออฟไลน์
* **เนื้อหาบนสไลด์:**
  * **1. ตาราง `player_profiles` (สถิติและโปรไฟล์ผู้เล่น):**
    * `id` (UUID): รหัสผู้เล่น [PK] · `username` (TEXT): ชื่อแสดงผล
    * `gems` (INT): อัญมณีสะสม · `mmr` (INT): คะแนนจัดอันดับ (Default: 1000)
    * `wins` / `losses` (INT): สถิติแพ้ชนะ
    * `owned_frames` (ARRAY): รายการกรอบรูปภาพที่ครอบครอง
    * `equipped_frame` (TEXT): กรอบที่ติดตั้ง (Default: `ARRAY['frame_default']` ตามเล่ม)
    * `selected_character` (INT): หมายเลขตัวละครที่สวมใส่
  * **2. ตาราง `rooms` (ข้อมูลเซสชันห้องเกม):**
    * `id` (BIGINT): รหัสห้อง [PK] (Identity) · `room_code` (TEXT): รหัสเข้าห้องแบบสุ่ม
    * `session_name` (TEXT): ชื่อฉากที่ใช้โหลด · `host_name` (INT): ผู้เล่นที่สร้างห้อง
    * `player_count` (INT): จำนวนเป้าหมาย · `status` (TEXT): สถานะห้อง (waiting/matched)
  * **3. ตาราง `matchmaking_queue` (คิวระบบจับคู่ผู้เล่น):**
    * `id` (BIGINT): รหัสคิว [PK] · `player_id` (TEXT): ไอดีผู้เล่น [FK] · `status` (TEXT): สถานะคิว
    * `room_code` / `room_id` (BIGINT): รหัส/ไอดีห้องที่ได้จับคู่ [FK]
    * `matched_player_id` (TEXT): รหัสผู้เล่นคู่แข่ง · `target_player_count` (INT): จำนวนผู้เล่น
    * `search_request_id` (TEXT): รหัสอ้างอิงคำขอ · `matched_at` (TIMESTAMPTZ): เวลาที่จับคู่สำเร็จ
  * **4. โครงสร้างไฟล์คลังข้อสอบออฟไลน์ (`quiz_database.json`):**
    * `version` (TEXT) / `totalQuestions` (INT) / `questions` (ARRAY)
    * รายละเอียดข้อสอบย่อย: `id` (TEXT), `category` (TEXT), `difficulty` (TEXT), `question` (TEXT), `choices` (ARRAY), `correctIndex` (INT)
    * **สาธิตระบบ (Live Demo):**
    * ลิงก์เข้าระบบจัดการข้อสอบ: [https://startup-city-quiz-thanapat.surge.sh/quiz_admin.html](https://startup-city-quiz-thanapat.surge.sh/quiz_admin.html)
* **รูปภาพประกอบ:**
  * `[รูป: แผนผัง Database ER-Diagram แสดงตารางหลักทั้ง 3 และความสัมพันธ์]` (ดูรูปได้ที่: [supabase_database_schema.png](file:///d:/ProjectGameCard/GameCardClient/Docs/supabase_database_schema.png))
* **บทพูดนำเสนอ (Presenter Note):**
  * *"สำหรับการออกแบบฐานข้อมูลระบบแกนหลัก เราอ้างอิงตามในเล่มรายงาน 3 ตารางหลักครับ คือ player_profiles สำหรับเก็บข้อมูล MMR และของสะสมผู้เล่น, rooms สำหรับเก็บข้อมูลห้อง และ matchmaking_queue สำหรับระบบจัดคิวจับคู่แบบเรียลไทม์ครับ"*
  * *"และในระบบยังมีไฟล์โครงสร้างข้อมูลแบบ JSON ชื่อ quiz_database.json สำหรับเก็บคลังคำถามวิชาการแบบออฟไลน์ ซึ่งเราสามารถเปิดและบริหารจัดการคลังคำถามนี้ได้อย่างสะดวกผ่านหน้าเว็บพอร์ทัล Quiz Admin ตามลิงก์สไลด์นี้เลยครับ ประกอบด้วยข้อมูลโจทย์, ตัวเลือกตอบ 4 ตัวเลือก และดัชนีเฉลยที่ถูกต้อง ซึ่งเราอัปเดตและส่งออกไฟล์กลับมาทับในตัวเกมได้ทันทีครับ"*

### สไลด์ที่ 7: ระบบห้องพักและการจับคู่ผู้เล่น (Matchmaking & Lobby System)
* **หัวข้อสไลด์:** โหมดการเล่นที่รองรับและระบบคิวจับคู่ป้องกันข้อมูลชนกัน
* **เนื้อหาบนสไลด์:**
  * **โหมดการเล่นที่ระบบรองรับ (Game Modes):**
    * **โหมดเล่นคนเดียว (Single Player):** แข่งขันกับบอทคอมพิวเตอร์จำลอง (Rule-Based Bot AI)
    * **โหมดสร้างห้องส่วนตัว (Private Lobby):** สร้างและแชร์รหัสห้อง (Room Code) เล่นกับกลุ่มเพื่อน 2-4 คน
    * **โหมดจับคู่เล่นอัตโนมัติ (Auto Matchmaking Queue):** จัดคิวผู้เล่น 2-4 คนเข้าห้องอัตโนมัติผ่านเซิร์ฟเวอร์
    * **โหมดควิซรายวัน (Daily Quiz):** โหมดตอบคำถามแบบเล่นเดี่ยวเพื่อประเมินความรู้และสะสม Gems
  * **ตรรกะระบบจับคู่ (Matchmaking Flow):**
    * ผู้เล่นกดจับคู่ → Client ส่งคำสั่งเข้า Supabase Edge Functions → เรียกใช้ Database Function ชื่อ `claim_matchmaking_room` บนฐานข้อมูล
  * **วิธีการกันข้อมูลชนกัน (Race Condition Prevention):**
    * ใช้คำสั่ง **`SELECT ... FOR UPDATE`** เพื่อทำ Row-level Locking ล็อกแถวขณะรันธุรกรรมจัดหาห้อง
    * ใช้ **Unique Partial Index** บน ID ผู้เล่นในสถานะ 'waiting' ป้องกันการลงทะเบียนเข้าคิวซ้ำซ้อน
* **รูปภาพประกอบ:**
  * `[รูป: แผนภาพโฟลว์การทำงาน (Sequence Diagram) ของการทำ Matchmaking ระหว่าง Client กับ claim_matchmaking_room บน DB]`
* **บทพูดนำเสนอ (Presenter Note):**
  * *"ตัวเกมของเรามีการออกแบบให้รองรับ 4 โหมดการเล่นเพื่อการเรียนรู้ครับ คือโหมด Single Player เล่นกับบอท, โหมด Private Lobby เล่นในกลุ่มเพื่อน, โหมด Auto Matchmaking จับคู่ออนไลน์อัตโนมัติ และโหมดตอบควิซประเมินความรู้รายวันเพื่อรับ Gems"*
  * *"และเพื่อดูแลระบบจับคู่ออนไลน์นี้ให้รวดเร็วและเสถียรที่สุด เมื่อผู้เล่นกดจับคู่ ตัวเกมจะส่งคำขอไปเรียกใช้งาน RPC Function ชื่อ claim_matchmaking_room บน Supabase ซึ่งมีการแก้ไขปัญหา Race Condition (ข้อมูลชนกันขณะกดเข้าห้องพร้อมกัน) โดยการใช้ Row-level Locking ผ่าน SELECT FOR UPDATE เพื่อล็อกแถวในคิวระหว่างการจัดสรร และสร้าง Unique Partial Index บนสถานะ waiting ป้องกันปัญหารายชื่อผู้เล่นค้างในคิวซ้ำซ้อนครับ"*

### สไลด์ที่ 8: บอทคอมพิวเตอร์จำลอง (Rule-Based Bot AI)
* **หัวข้อสไลด์:** ระบบปัญญาประดิษฐ์ของคอมพิวเตอร์ (Bot AI)
* **เนื้อหาบนสไลด์:**
  * **ตรรกะกฎเกณฑ์ 4 ลำดับการตัดสินใจ (4-Level Priority System):**
    1. **ซื้อการ์ดเพื่อชนะ:** ตรวจสอบและซื้อการ์ดทันทีหากแต้มดาวจะครบ 20 คะแนน
    2. **ซื้อการ์ดคุ้มค่าสุด:** คำนวณความคุ้มค่าจากแต้มและราคาเพื่อเลือกซื้อใบที่ดีที่สุด
    3. **จองการ์ดระดับสูง:** เลือกจองการ์ด Tier 3 เพื่อสกัดคนเล่นและเก็บเหรียญทองพิเศษ
    4. **หยิบเหรียญสะสม:** หยิบเหรียญที่ยังขาดสำหรับการ์ดเป้าหมายสูงสุด
  * **4 บุคลิกจำลอง (Archetypes):** Balanced (สมดุล) · Aggressive (เน้นแต้มสูง) · Hoarder (เน้นจองตุนของ) · Specialist (โฟกัสเฉพาะสี)
  * > **⚠️ หมายเหตุข้อแตกต่างระหว่าง TOR และโค้ดจริง:** 
    > * **ความแม่นยำในการตอบควิซ:** TOR ระบุ 100% แต่โค้ดจริงสุ่ม 40–80% (เพื่อให้ผู้เล่นมีโอกาสชนะเทิร์นบอท)
    > * **จังหวะเวลาตอบควิซ:** TOR ระบุ 5 วินาทีสุดท้าย แต่โค้ดจริงสุ่ม 1–10 วินาที เพื่อความเป็นธรรมชาติ
* **รูปภาพประกอบ:**
  * `[รูป: โฟลว์ชาร์ตการตัดสินใจของบอท Rule-Based 4 ระดับ และรูปสัญลักษณ์ตัวละครที่เป็นตัวแทนของแต่ละสายอาชีพ]`
* **บทพูดนำเสนอ (Presenter Note):**
  * *"สำหรับโหมดเล่นคนเดียว เราสร้างบอท AI แบบ Rule-Based ที่มี 4 ลำดับตรรกะและ 4 บุคลิก เพื่อให้การเล่นไม่จำเจครับ อย่างไรก็ตาม ในส่วนของบอทตอบควิซ เราได้ปรับปรุงจากที่เขียนไว้ใน TOR ว่าจะตอบถูก 100% มาเป็นการสุ่มตอบถูก 40-80% แทน เพื่อให้ตัวเกมมีความสมดุลและผู้เล่นสามารถเอาชนะบอทได้ครับ"*

### สไลด์ที่ 9: ความมั่นคงปลอดภัยและการป้องกันการโกง (Security & Anti-Cheat)
* **หัวข้อสไลด์:** ความมั่นคงปลอดภัยของระบบเครือข่ายและข้อมูล
* **เนื้อหาบนสไลด์:**
  * **Server-Authoritative Design:**
    * ทุกการคำนวณคะแนน MMR หรือสิทธิ์การได้รับ Gem รางวัลตอนจบเกม จะประมวลผลบนเซิร์ฟเวอร์คลาวด์เท่านั้น ป้องกันการดัดแปลงค่าข้อมูลจากตัวเกม (Client)
  * **Row-Level Security (RLS) Policies:**
    * ผู้เล่นทั่วไป (Role: `anon`/`authenticated`) มีสิทธิ์อ่านคลังข้อสอบและตารางจัดอันดับเท่านั้น ไม่มีสิทธิ์เขียนลงตารางหลัก ยกเว้นการทำรายการผ่าน Edge Functions
  * **OTP Verification Encryption:**
    * รหัส OTP จะบันทึกในรูปแบบ SHA-256 Hash และจำกัดสิทธิ์การเดารหัสผ่านตัวแปร `attempts` ป้องกัน Brute-force
* **รูปภาพประกอบ:**
  * `[รูป: แผนภาพแสดงการบล็อกคำสั่งสิทธิ RLS บน Supabase จากตัวแฮกเกอร์ฝั่ง Client]`
* **บทพูดนำเสนอ (Presenter Note):**
  * *"ความมั่นคงปลอดภัยเป็นสิ่งสำคัญ โครงงานนี้ใช้สถาปัตยกรรมแบบ Server-Authoritative ฝั่ง Client จะส่งขึ้นไปแค่อันดับที่เล่นจบ ส่วนการบวกคะแนน MMR หรือ Gems จะคำนวณบนคลาวด์ทั้งหมด และเราใช้นโยบาย RLS บน Supabase ทำให้ผู้เล่นไม่สามารถเขียนแก้ค่าหรือโกงระบบคะแนนได้ครับ"*
