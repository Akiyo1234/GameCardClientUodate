## 🎲 ส่วนที่ 3 — กลไกเกมแบบละเอียด (กติกาที่ต้องอธิบายได้)

### 3.1 ทรัพยากร & เหรียญ
- เหรียญทรัพยากร 5 สี = **CPU, RAM, Network, Storage, Security**
- เหรียญ **Gold (Wildcard)** = แทนสีใดก็ได้ — **ห้ามหยิบตรงๆ** ได้จากการ "จองการ์ด" เท่านั้น
- ถือเหรียญรวมกันได้ไม่เกิน **10 อัน**

### 3.2 การ์ดโมดูลซอฟต์แวร์ (Engine-Building)
- การ์ดแต่ละใบมี **ต้นทุน** (เหรียญที่ต้องจ่าย) และ **แต้ม (Stars)**
- ซื้อการ์ดแล้วได้ **โบนัสถาวร 1 สี** = ส่วนลดต้นทุนการ์ดใบต่อๆ ไป (นี่คือหัวใจ "Engine-Building" ของ Splendor — ยิ่งซื้อยิ่งถูกลง)
- มี 3 Tier เรียงจากถูก/แต้มน้อย (T1) ไปแพง/แต้มเยอะ (T3)

### 3.3 แอคชั่นในแต่ละเทิร์น (เลือกได้ 1 อย่าง)
1. **หยิบเหรียญ (Collect):** 3 สีต่างกัน *หรือ* 2 สีเดียวกัน (ถ้ากองนั้นเหลือ ≥ 4)
2. **ซื้อการ์ด (Purchase):** จ่ายเหรียญตามต้นทุน (หักโบนัสที่มีก่อน) → ได้แต้ม + โบนัส
3. **จองการ์ด (Reserve):** เก็บการ์ดขึ้นมือ(สูงสุด 3 ใบ) + ได้ Gold 1 เหรียญ — ใช้ตัดหน้าคู่แข่ง/ล็อกการ์ดแพง

### 3.4 ขุนนาง (Nobles)
- มี 8 ใบ ระบบ **เช็คให้อัตโนมัติทุกจบเทิร์น** — ถ้าผู้เล่นมีโบนัสการ์ดครบเงื่อนไข ขุนนางจะมาหาเองและให้แต้มเพิ่ม

### 3.5 เงื่อนไขชนะ
- ใครถึง **20 แต้ม** ก่อน = ชนะ
- ⚠️ **จุดที่ต้องระวัง:** เล่ม (Scope 3.4) เขียนว่า "เล่นให้จบรอบนั้นก่อนเพื่อให้ทุกคนเดินเท่ากัน" แต่ **โค้ดจริงจบเกมทันทีที่มีคนถึง 20** — ดูส่วนที่ 8 ข้อ 5

### 3.6 ควิซแทรก (จุดเด่นด้านการศึกษา)
- ทุกๆ N รอบ เกมจะหยุดแล้วเด้งคำถามคอมพิวเตอร์ 1 ข้อ (4 ตัวเลือก) ให้ทุกคนตอบพร้อมกัน จับเวลา 10 วินาที
- **ตอบถูก + เร็วที่สุด = ได้เดินเป็นคนแรกในรอบถัดไป** (เป็นการเอาความรู้มาแปลงเป็นความได้เปรียบในเกม → จูงใจให้ตั้งใจเรียน)

## ⚙️ ส่วนที่ 4 — เจาะระบบสำคัญ (เนื้อหาที่ใช้พรีเซนต์ + ตอบคำถามเชิงลึก)

### 4.1 บอท AI แบบ Rule-Based (โหมดเล่นคนเดียว) ⭐ จุดขาย
บอท **ไม่ใช่ Machine Learning** แต่เป็น **ระบบตรรกะเชิงกฎเกณฑ์ (Rule-Based) ที่มีลำดับการตัดสินใจ 4 ขั้น** ทุกเทิร์นบอทจะไล่เช็คตามลำดับนี้ เจออันไหนทำได้ก่อนทำเลย:

| ลำดับ | เงื่อนไข | การกระทำ |
|---|---|---|
| **1. ปิดเกม** | มีการ์ดที่ซื้อแล้วทำให้แต้มรวม ≥ 20 | ซื้อทันที (ชนะ) |
| **2. ซื้อใบที่คุ้มสุด** | มีการ์ดที่ซื้อไหว | ให้คะแนน = `แต้ม × น้ำหนัก − ต้นทุน` แล้วเลือกใบดีสุด |
| **3. จองเชิงรุก** | ขาดเหรียญซื้อ T3 อยู่นิดเดียว | จองล็อกการ์ดไว้ + ได้ Gold |
| **4. เก็บของ** | ทำ 1–3 ไม่ได้ | หยิบเหรียญสีที่ "ต้องการมากที่สุด" บนกระดาน |

**ของเด็ดที่ควรอวด:** บอทมี **4 บุคลิก (Archetype)** คงที่ตามที่นั่ง ทำให้ตัดสินใจต่างกันแม้เจอสถานการณ์เดียวกัน:
- **Balanced** — มาตรฐาน
- **Aggressive** — เน้นการ์ดแต้มสูง ไม่ค่อยจอง (น้ำหนักแต้ม ×2.0)
- **Hoarder** — ชอบจอง/สะสมทอง เลือกการ์ดถูก
- **Specialist** — โฟกัสเก็บ 2 สีที่ถนัด

> มี "ความไม่แน่นอน" (suboptimalChance) ให้บอทบางครั้งเลือกตัวเลือกอันดับรอง → ไม่เล่นซ้ำซากเป็นหุ่นยนต์เกินไป

**ทำไมเลือก Rule-Based ไม่ใช่ ML?** → ตอบในส่วนที่ 7 (คำถามฮิต)

### 4.2 ควิซ & การชิงเทิร์น
- Host (Master Client) เป็นคนสุ่มคำถามแล้ว **broadcast** ให้ทุกเครื่องเห็นข้อเดียวกัน (กันโกง/กันเห็นไม่ตรงกัน)
- ระบบวัดทั้ง **ความถูก** และ **ความเร็วระดับเสี้ยววินาที** แล้วจัดลำดับเทิร์นใหม่ (`ApplyNewTurnOrder`)
- ในโหมดเล่นคนเดียว ระบบ **จำลองคำตอบของบอท** (สุ่มถูก 40–80%, สุ่มความเร็ว 1–10 วิ) เพื่อให้มีคู่แข่งชิงเทิร์น

### 4.3 Matchmaking + การกัน Race Condition ⭐ จุดขายเชิง DB
- ผู้เล่นกด "หาคู่" → client ยิงขึ้น **Supabase Edge Function** ชื่อ `matchmaking` → ฝั่ง server เรียก **Database Function `claim_matchmaking_room`**
- **ปัญหาที่แก้:** ถ้า 2 คนกดพร้อมกัน อาจถูกจับเข้าคนละห้อง/ห้องซ้ำ (Race Condition)
- **วิธีแก้ (พูดให้อาจารย์ฟังได้):**
  1. ใช้ **`SELECT ... FOR UPDATE`** ล็อกแถวคิวระดับธุรกรรม (transaction)
  2. ใช้ **Unique Partial Index** บน `matchmaking_queue(player_id) WHERE status='waiting'` → 1 คนมีได้แค่ 1 คิว เป็นไปไม่ได้ที่จะซ้ำ
  3. client poll สถานะทุก 1.5 วิ จนได้ห้อง แล้วเข้าร่วม Photon session เดียวกัน
- มี timeout กันคิวค้าง (stale) ที่ 300 วินาที

### 4.4 การซิงค์สถานะผ่าน Photon Fusion (Shared Mode)
- **Shared Mode** = ไม่มีเซิร์ฟเวอร์กลางตัวเดียว แต่มี **Master Client** ทำหน้าที่เป็น "ผู้ตัดสิน" (authority) เรื่องกระดาน/ควิซ
- Host จะ **broadcast 3 snapshot**: สถานะกระดาน (Board), เศรษฐกิจ/เหรียญ (Economy), ลำดับเทิร์น (Turn)
- ⭐ **เทคนิคแก้บั๊กที่เจอจริง (พูดได้เลยว่าเจอปัญหานี้แล้วแก้):** ผู้เล่นที่เข้าห้องช้า (late-joiner) จะ **"ดึง" สถานะเต็มจาก host เอง (`RequestFullState`)** แทนที่จะรอ host "ส่ง" มา — เพราะตอนเพิ่งเข้า ฉากอาจโหลดไม่เสร็จ ทำให้ broadcast หลุดและเห็นกระดานไม่ตรงกัน → เปลี่ยนจาก **push เป็น pull** เพื่อกัน desync
- ถ้าผู้เล่นหลุดกลางเทิร์น/หมดเวลา → `ForceEndTurn()` ให้ host บังคับจบเทิร์นแทน ไม่ให้เกมค้าง

### 4.5 ความปลอดภัย & Anti-Cheat ⭐ จุดขายที่อาจารย์ชอบ
- **Server-Authoritative:** ตอนจบเกม client ส่งขึ้น DB แค่ **"อันดับที่ได้ + จำนวนผู้เล่น"** เท่านั้น แล้ว **server คำนวณ MMR/Gems เอง** → client **ปลอมค่า MMR/เพชรลง DB ไม่ได้**
- **RLS (Row Level Security):** ตาราง `player_profiles` ตั้งให้ client (authenticated) **อ่านได้อย่างเดียว** เขียนได้เฉพาะ `service_role` ผ่าน Edge Function
- **ราคาร้านค้าอยู่ที่ server:** ตาราง `shop_items` เก็บราคาจริง → client แก้ราคาเองไม่ได้
- **OTP ยืนยันอีเมล:** เก็บเป็น **SHA-256 hash ไม่เก็บเลขตรง** มี `expires_at` (หมดอายุ) และ `attempts` (จำกัดจำนวนครั้งเดา)

### 4.6 ฐานข้อมูล (Supabase / PostgreSQL) — 8 ตาราง
| ตาราง | หน้าที่ |
|---|---|
| `player_profiles` | โปรไฟล์หลัก: gems, mmr, wins, losses, กรอบที่มี/ที่ใส่, ตัวละคร (1:1 กับ `auth.users`) |
| `rooms` | ห้องเกมที่จับคู่สร้าง (ผูกกับ Photon session) |
| `matchmaking_queue` | คิวจับคู่ออนไลน์ (มี RPC `claim_matchmaking_room`) |
| `shop_items` | ราคาไอเทมร้านค้า (source of truth กันโกงราคา) |
| `daily_quiz_claims` | กันรับรางวัลควิซรายวันซ้ำ (1 คน/วัน) |
| `quiz_patches` | ชุด/แพ็กข้อสอบ (เปิด-ปิด active ได้) |
| `quiz_questions` | คลังคำถาม (โจทย์, 4 ตัวเลือก jsonb, เฉลย) ผูกกับ patch |
| `otp_codes` | รหัส OTP ยืนยันอีเมล (เก็บ hash) |

> **จุดขาย:** ระบบควิซเป็น **"Patch System"** — เพิ่ม/แก้ข้อสอบในฐานข้อมูลได้ **โดยไม่ต้อง build เกมใหม่** เพราะตัวเกมดึงคำถามจาก patch ที่ active ผ่าน RPC

ถ้าอาจารย์ถาม "โปรเจคนี้เด่นกว่าการเอาเกม Splendor มาทำใหม่ตรงไหน" ให้ชู 6 ข้อนี้:

## ❓ ส่วนที่ 7 — คลังคำถาม-คำตอบ (เตรียมรับมืออาจารย์) ⭐⭐⭐

> นี่คือส่วนสำคัญที่สุด ซ้อมพูดคำตอบให้เป็นธรรมชาติ อย่าท่อง

### กลุ่ม A — แนวคิด / เหตุผล (Conceptual)

**Q1: ทำไมเลือกเกม Splendor เป็นต้นแบบ?**
> เพราะกลไกหลักของ Splendor คือ **การบริหารทรัพยากรและการต่อยอด (engine-building)** ซึ่งแมปเข้ากับแนวคิด "การจัดสรรทรัพยากรระบบคอมพิวเตอร์" ได้ตรงมาก — ทรัพยากรมีจำกัด ต้องวางแผนใช้ และการลงทุนช่วงแรกทำให้ช่วงหลังได้เปรียบ (เหมือนโบนัสส่วนลด) อีกทั้งกติกากระชับ เรียนรู้ง่าย เหมาะเป็นสื่อการสอน

**Q2: เกมนี้ "สอน" อะไร และวัดผลการเรียนรู้ยังไง?**
> สอน 2 ชั้น — ชั้นแรกคือ **แนวคิดทรัพยากรระบบ 5 ด้าน** (CPU/RAM/Network/Storage/Security) ผ่านการเล่นซ้ำๆ จนซึมซับ ชั้นที่สองคือ **ความรู้คอมพิวเตอร์เชิงวิชาการ** ผ่านควิซแทรกและ Daily Quiz ส่วนการวัดผล ใช้ **แบบสอบถามความพึงพอใจ (Likert 5 ระดับ) กับผู้ทดลอง 15 คน ได้ค่าเฉลี่ย 4.50** อยู่ในระดับมากที่สุด

**Q3: ความใหม่/contribution ของงานคืออะไร ในเมื่อ Splendor มีคนทำดิจิทัลแล้ว?**
> เกม Splendor ดิจิทัลที่มีอยู่ (เช่น Ephod) เน้นความบันเทิงล้วน **ไม่มีเนื้อหาวิชาการ** งานนี้ต่างตรงที่ (1) **รีธีมเป็นการศึกษา IT** (2) **ฝังควิซเข้าไปในกลไกเกม** ให้ความรู้กลายเป็นความได้เปรียบ (3) ทำเป็น **ระบบ Full-Stack multiplayer + cloud** ที่ใช้งานได้จริง ไม่ใช่ต้นแบบบนกระดาษ

**Q4: ทำไมต้องเป็น "เกม" ทำไมไม่ทำแอปสอน/ควิซตรงๆ?**
> เพราะใช้หลัก **Gamification** — การแข่งขัน, อันดับ MMR, รางวัลเพชร, การปลดล็อกกรอบ สร้าง **แรงจูงใจภายใน** ให้ผู้เรียนกลับมาทบทวนเองโดยสมัครใจ ซึ่งการอ่านตำราเฉยๆ ทำไม่ได้

### กลุ่ม B — เทคนิค (Technical) — อาจารย์สาย CS จะเจาะตรงนี้

**Q5: Photon Fusion "Shared Mode" คืออะไร ต่างจาก Host/Server Mode ยังไง ทำไมเลือก?**
> Shared Mode คือโหมดที่ **ไม่มีเซิร์ฟเวอร์ authority ตัวเดียว** แต่ละ NetworkObject มี "เจ้าของสถานะ" (State Authority) กระจายกัน เหมาะกับเกม session เล็ก ผู้เล่นน้อย และ **ประหยัด** เพราะไม่ต้องรัน dedicated server เอง ผมเลือกเพราะเกมเรา 2–4 คน แต่ผมยังให้ **Master Client ทำหน้าที่เป็นผู้ตัดสิน** เรื่องสุ่มคำถามควิซและสถานะกระดาน เพื่อกันความขัดแย้งของข้อมูล

**Q6: ถ้าผู้เล่น 2 คนกดหาคู่พร้อมกันเป๊ะ ระบบกันการจับคู่ผิดยังไง? (Race Condition)**
> กัน 2 ชั้น — ชั้นแรกที่ระดับฐานข้อมูลใช้ **`SELECT ... FOR UPDATE`** ล็อกแถวคิวในธุรกรรม ทำให้ 2 request เข้ามาแก้พร้อมกันไม่ได้ ต้องรอกัน ชั้นที่สองมี **unique partial index** บน `player_id` เฉพาะแถวที่ `status='waiting'` ทำให้คนเดียวมีคิวซ้อนไม่ได้เด็ดขาด

**Q7: ผู้เล่นโกงคะแนน MMR หรือเพชรได้ไหม?**
> ไม่ได้ครับ ระบบเป็น **Server-Authoritative** — ตอนจบเกม client ส่งขึ้น server แค่ "อันดับที่จบ + จำนวนผู้เล่น" แล้ว **server คำนวณ MMR/เพชรเองด้วยสูตรเดียวกัน** ที่ใช้โชว์ฝั่ง client นอกจากนี้ตาราง profile ตั้ง **RLS ให้ client เขียนไม่ได้** เขียนได้เฉพาะ Edge Function ฝั่ง server เท่านั้น

**Q8: บอทเป็น AI/Machine Learning ไหม?**
> ไม่ใช่ ML ครับ เป็น **Rule-Based (ระบบกฎเกณฑ์)** ที่มี **ลำดับการตัดสินใจ 4 ขั้น** บวก heuristic ให้คะแนนการ์ด ผมเลือก Rule-Based เพราะ (1) **อธิบายได้ทุกการตัดสินใจ** (explainable) (2) **ไม่ต้อง train ไม่ต้องมี dataset** (3) **เบา รันบนมือถือได้ทันที** และ (4) สำหรับเกมกฎตายตัวแบบนี้ Rule-Based ที่ออกแบบดีก็เล่นเก่งพอท้าทายแล้ว ส่วน ML จะ over-engineer เกินจำเป็น

**Q9: แล้วบอททำให้มันไม่น่าเบื่อยังไง ในเมื่อเป็นกฎตายตัว?**
> ผมเพิ่ม **4 บุคลิก (archetype)** ที่ผูกกับตำแหน่งที่นั่ง ปรับน้ำหนัก/เกณฑ์การตัดสินใจต่างกัน เช่น Aggressive เน้นการ์ดแต้มสูง Hoarder ชอบจองเก็บของ และใส่ **ความน่าจะเป็นที่บอทจะเลือกตัวเลือกอันดับรอง** ทำให้ไม่เล่นเหมือนกันเป๊ะทุกตา ดูเป็นมนุษย์ขึ้น

**Q10: ทำไมเลือก Supabase ไม่ใช้ Firebase?**
> เพราะ Supabase ใช้ **PostgreSQL จริง** ผมจึงเขียน **SQL, RPC function, RLS, transaction** ได้เต็มที่ ซึ่งจำเป็นกับการกัน race condition ในระบบจับคู่ อีกทั้งเป็น open-source และ free tier เพียงพอกับโครงงาน ส่วน Firebase เป็น NoSQL ทำ logic ระดับ transaction/row-lock ได้ยากกว่า

**Q11: ข้อมูลกระดานของแต่ละเครื่องเห็นไม่ตรงกันจะทำยังไง?**
> ผมให้ **Master Client เป็น authority** แล้ว broadcast snapshot ของกระดาน/เหรียญ/เทิร์น และเจอปัญหาจริงว่าคนเข้าห้องช้าจะ "พลาด" broadcast เพราะฉากยังโหลดไม่เสร็จ ผมเลยแก้เป็นให้ client ที่พร้อมแล้ว **"ขอสถานะเต็มจาก host เอง" (pull)** แทนการรอรับ (push) ทำให้ late-joiner sync ตรงเสมอ

**Q12: ออกแบบฐานข้อมูลกี่ตาราง มีความสัมพันธ์ยังไง?**
> 8 ตารางหลัก ตัวอย่างความสัมพันธ์: `player_profiles` ผูก 1:1 กับ `auth.users`, `matchmaking_queue` อ้างถึง `rooms` (FK), `quiz_questions` อ้างถึง `quiz_patches` (FK แบบ cascade) ออกแบบให้ข้อมูลถาวร (โปรไฟล์/คะแนน) แยกจากข้อมูลชั่วคราว (คิว/ห้อง) ชัดเจน

**Q13: ระบบควิซแก้ข้อสอบต้อง build เกมใหม่ไหม?**
> ไม่ต้องครับ ผมทำเป็น **Patch System** — คำถามเก็บใน `quiz_questions` ผูกกับ `quiz_patches` ตัวเกมดึงเฉพาะ patch ที่ `is_active=true` ผ่าน RPC ดังนั้นแก้ข้อสอบในฐานข้อมูลแล้วเกมอัปเดตเองทันที (นี่เป็นฐานสำหรับต่อยอดเป็น Instructor Dashboard ในอนาคต)

### กลุ่ม C — การออกแบบ/ความสมดุล (Design)

**Q14: ทำไมตั้งเป้าหมายที่ 20 แต้ม? ทำไมควิซทุก N รอบ?**
> เป็นค่าที่ได้จาก **การปรับสมดุล (balancing) จากการทดลองเล่น** ให้เกมจบในเวลาที่กำลังดี ไม่สั้นไม่ยืดเกิน ส่วนความถี่ควิซก็จูนให้แทรกความรู้ได้สม่ำเสมอโดยไม่ขัดจังหวะเกมจนน่ารำคาญ *(ดู ⚠️ ส่วนที่ 8 เรื่องตัวเลขควิซในโค้ดก่อนตอบ)*

**Q15: ทำไม MMR ใช้สูตรแบบ DOTA2 ไม่ใช่ Elo?**
> Elo ออกแบบมาสำหรับ **1v1** และคิดจากส่วนต่างเรตติ้งคู่แข่ง แต่เกมเราเป็น **2–4 คน จัดอันดับ** ผมเลยใช้สูตรแบบให้คะแนน/หักตามอันดับที่จบ (placement-based) แบบ DOTA2 ซึ่งเข้าใจง่ายและเหมาะกับ multiplayer มากกว่า

### กลุ่ม D — ข้อจำกัด (Limitations)

**Q16: จุดอ่อนของระบบคืออะไร?**
> 3 เรื่องหลัก (1) **บอทเป็นกฎตายตัว** ยังไม่ปรับความยากตามฝีมือผู้เล่นอัตโนมัติ (2) **ยังไม่มีหน้าจัดการข้อสอบสำหรับอาจารย์** ต้องแก้ผ่านฐานข้อมูลโดยตรง (3) **ยังไม่มีระบบ chat/emoji** ระหว่างผู้เล่น — ทั้ง 3 ข้อนี้ผมระบุไว้เป็น **งานในอนาคต** แล้ว

**Q17: ทดสอบกับผู้ใช้จริงกี่คน เพียงพอไหม?**
> ทดลองกับนิสิต 15 คน ผ่านแบบสอบถาม Likert 5 ระดับ ได้ค่าเฉลี่ย 4.50 (S.D. 0.54) ซึ่งเพียงพอสำหรับการประเมินเชิงความพึงพอใจในระดับโครงงาน แต่ผมยอมรับว่าถ้าจะวัด **ผลสัมฤทธิ์การเรียนรู้** จริงๆ ควรทำ pre-test/post-test กับกลุ่มตัวอย่างใหญ่ขึ้น ซึ่งเป็นข้อเสนอแนะสำหรับงานต่อไป

## ⚠️ ส่วนที่ 8 — จุดที่เอกสารกับโค้ดไม่ตรงกัน (แก้ก่อนสอบ!) ⭐ สำคัญมาก

ผมตรวจโค้ดจริงเทียบกับเล่มเอกสาร เจอ **5 จุดที่ไม่ตรงกัน** ถ้าอาจารย์เปิดโค้ดดูหรือเล่นเกมจริงจะเห็นไม่ตรงกับที่เขียน **แนะนำให้เลือกทางใดทางหนึ่ง: แก้โค้ดให้ตรงเล่ม หรือแก้เล่มให้ตรงโค้ด ก่อนวันสอบ**

| # | เรื่อง | เล่มเขียนว่า | โค้ดจริงเป็น | คำแนะนำ |
|---|---|---|---|---|
| 1 | **ความถี่ควิซ** | ทุก **3 รอบ** (Abstract, 3.6, 7) | `quizInterval = 5` → ทุก **5 รอบ** | แก้โค้ดเป็น `3` ง่ายสุด (แก้ 2 บรรทัด) |
| 2 | **เวลาตอบควิซ** | **20 วิ** (Scope 3.5) | `timeLimit = 10f` → **10 วิ** | แก้เล่ม 3.5 เป็น 10 วิ (บทผล 6.4 ก็เขียน 10 วิอยู่แล้ว) |
| 3 | **บอทตอบควิซถูก** | **100%** (Scope 3.5) | สุ่ม **40–80%** | แก้เล่มเป็น 40–80% (ดีกว่า เพราะ 100% ผู้เล่นชนะเทิร์นไม่ได้) |
| 4 | **จังหวะบอทตอบ** | "5 วิสุดท้าย" (3.5, 7.2) | สุ่ม **1–10 วิ** ตลอดช่วง | แก้เล่มเป็น "สุ่มทั้งช่วง" หรือแก้โค้ดให้ตอบช่วงท้าย |
| 5 | **เงื่อนไขจบเกม** | เล่นจบรอบก่อน (ให้เดินเท่ากัน) — Scope 3.4 | **จบทันทีที่ถึง 20 แต้ม** | ตัดสินใจ: ถ้าจะคงโค้ด ให้แก้เล่ม 3.4 |

**รายละเอียดแต่ละจุด (เผื่ออาจารย์ถามเจาะ):**

- **#1 ควิซทุก 5 รอบ:** ไฟล์ `GameController.cs` ตั้ง `quizInterval = 5` และ `onlineQuizTurnInterval = 5` เงื่อนไขใน `GameController.Turns.cs` คือ `(รอบ-1) % 5 == 0` → ควิซจะเด้งตอนเริ่มรอบที่ 6, 11, 16 (บวกควิซรอบแรกตอนเปิดเกม) **ถ้าต้องการ "ทุก 3 รอบ" ตามเล่ม เปลี่ยน `5` เป็น `3` ทั้งสองตัว**

- **#3 + #4 พฤติกรรมบอทควิซ:** อยู่ในฟังก์ชัน `SimulateOtherPlayers` (`QuizManager.cs`) — `botDifficulty = Random.Range(0.4f, 0.8f)` (โอกาสตอบถูก 40–80%) และ `botSpeed = Random.Range(1.0f, timeLimit)` (ตอบที่วินาทีสุ่ม 1–10) **หมายเหตุ:** บทคัดย่อ (Abstract) เขียนว่า "randomized quiz response delay" ซึ่ง **ตรงกับโค้ด** อยู่แล้ว มีแค่ Scope 3.5 กับ Discussion 7.2 ที่ขัดกัน

- **#5 จบเกมทันที:** `CheckWinCondition` ถูกเรียก **ทุกจบเทิร์น** ถ้าใครถึง 20 จะ `isGameOver = true` แล้วจบเลย (มีคอมเมนต์ในโค้ดระบุว่าตั้งใจเปลี่ยนจาก "เช็คตอนจบรอบ" มาเป็น "เช็คทันที") **ถ้าอาจารย์ถามเรื่องความยุติธรรม (คนเดินก่อนได้เปรียบ)** ให้ตอบว่าเป็น first-to-20 ที่จบทันทีเพื่อความชัดเจน หรือจะแก้กลับให้จบรอบตามเล่มก็ได้

> 💡 **ถ้ามีเวลาแก้แค่อย่างเดียว แก้ #1** (เปลี่ยน 5→3) เพราะเป็นตัวเลขที่อาจารย์เห็นง่ายสุดตอนเล่น และแก้ในโค้ดแค่ 2 บรรทัด ส่วน #2–#5 ถ้าไม่ทันแก้ ให้ **จำไว้และตอบตามโค้ดจริง** อย่าตอบตามเล่มที่ผิด

## 📖 ส่วนที่ 10 — อภิธานศัพท์ (ต้องนิยามได้ถ้าโดนถาม)

| คำ | นิยามสั้นๆ ที่พูดได้ |
|---|---|
| **Engine-Building** | กลไกเกมที่การลงทุนช่วงต้น (ซื้อการ์ด→ได้โบนัส) ทำให้ช่วงหลังทำแต้มเร็วขึ้นเรื่อยๆ |
| **Photon Fusion** | SDK เครือข่ายเรียลไทม์สำหรับเกม Unity ทำงานบน UDP |
| **Shared Mode** | โหมด Fusion ที่ไม่มี server กลางตัวเดียว, authority กระจายตาม object |
| **Master Client** | ผู้เล่นที่ถูกเลือกให้เป็น "ผู้ตัดสิน" สถานะร่วมในห้อง |
| **State Synchronization** | การทำให้สถานะเกมบนทุกเครื่องตรงกัน |
| **Race Condition** | สภาวะที่หลายคำสั่งทำงานพร้อมกันแล้วผลลัพธ์ผิดเพี้ยน |
| **`SELECT FOR UPDATE`** | คำสั่ง SQL ล็อกแถวข้อมูลในธุรกรรม กันแก้พร้อมกัน |
| **Server-Authoritative** | server เป็นผู้คำนวณ/ตัดสินค่าจริง client ปลอมไม่ได้ |
| **RLS (Row Level Security)** | กฎความปลอดภัยระดับแถวใน PostgreSQL คุมว่าใครอ่าน/เขียนแถวไหนได้ |
| **BaaS** | Backend-as-a-Service — บริการหลังบ้านสำเร็จรูปบนคลาวด์ (เช่น Supabase) |
| **RPC / Database Function** | ฟังก์ชันที่รันฝั่ง server/ฐานข้อมูล เรียกจาก client ได้ |
| **MMR** | Matchmaking Rating — คะแนนวัดฝีมือใช้จัดอันดับ/จับคู่ |
| **OTP** | One-Time Password — รหัสยืนยันใช้ครั้งเดียว (เราเก็บเป็น hash) |
| **Heuristic** | เกณฑ์/สูตรประมาณการช่วยตัดสินใจ (ในบอทใช้ให้คะแนนการ์ด) |
